# Peons with Benefits: public guild page

This public repository builds the Peons with Benefits guild page on GitHub Pages: DKP standings, each player's
raid role and loot, the raid calendar from Raid-Helper, a gallery of memories, events and raid kills, and the open
positions. It also shows guild facts, a public Capped DKP rules summary, recorded progression and account-level
raid attendance, with external character-profile links.

The site uses six tabs: **Overview** (guild facts and recruiting), **Raids** (upcoming raids, progression and
attendance), **Roster**, **DKP & loot** (standings, activity, officer uploader and data downloads), **Loot rules**,
and **Gallery**.
Only the selected tab is displayed. Existing section/player/event links still open the containing tab, and
browser Back/Forward restores navigation. Arrow keys, Home and End select tabs; Tab moves into their content.
The hero is shown only on Overview. All content stays in the server-rendered HTML for search engines, printing
and a readable single-page fallback when JavaScript is unavailable. No additional services or dependencies.

The **Officer uploader** section (`#uploader`, also linked from Overview) explains who needs the Windows desktop
tool, how it submits saved addon records for officer review, and how to set it up without sharing credentials
publicly. Its download button opens the latest public GitHub release rather than pinning an old build. Regular
raiders do not need the uploader; the separate in-game addon remains linked on CurseForge.

It was generated by `tools/capped_dkp_scaffold.py --public` from the CappedDKP project. The page has been rendered
and checked offline, but the live Raid-Helper and Wowhead connections have not been tested with real credentials
yet: check the first runs under **Actions**.

|---|---|---|
| `data/` | `standings.json` and `history.json`, already sanitized | Only the private ledger repository's mirror |
| `community.json` | Guild facts, Raid-Helper server, open positions, public logs links | Officers |

## How the page is built

**CappedDKP site** runs on every push to `main`, about every 15 minutes, and from **Actions → Run workflow**.
Scheduled runs often start late when GitHub is busy, so raid sign-up counts can lag by more than 15 minutes.

1. It checks `.cdkp/` against `.cdkp/TOOLKIT.json`.
2. It fetches the community data. Without its secret the raid calendar is shown as not set up; a source that fails
   shows its empty state, and the rest of the page still builds.
   - **Raid-Helper:** upcoming events for the next `raidHelper.days` days, saved as sign-up counts by role
     (Tank, Healer, Melee, Ranged). Absence, tentative, bench and declined sign-ups are not counted. When a sign-up
     matches exactly one visible roster character, its declared role/spec can also inform that character's roster
     summary; sign-up names and Discord IDs are not copied into the published event data.
   - **Wowhead:** names and quality of looted items, at most 50 new lookups per run. They are saved in
     `cache/item-cache.json` so each item is looked up once.
   - **Blizzard Armory:** the guild's public roster (names, profile links, level, class and rank), asked for
     only when `cache/armory-roster.json` is missing or at least 3 hours old, then saved there. Because the roster
     query has no specs, the workflow also reads character profile pages for their leading talent tree, up to 30
     profiles per run and at most once per character per day. Both Armory sources are undocumented and can change
     without notice. If a refresh fails, the saved roster and specs are kept; with none saved, the page shows the
     roster bundled in `.cdkp/` (read 2026-11-15).
3. It renders the page from `data/`, `community.json`, `gallery/` and the fetched data, and deploys it. When
   `CDKP_SITE_URL` is set, the page carries its canonical address and schema.org guild details, asks search engines
   to index it, and is deployed with `sitemap.xml` and `llms.txt` (a plain-text guide for AI assistants).

Until the private ledger first mirrors `data/`, the page says the standings are awaiting their first publication.

## One-time setup

The repository owner does this once. None of it is done for you.

1. Push the scaffold's output to `main` of this **public** repository.
2. **Settings → Pages → Build and deployment → Source:** *GitHub Actions*.
3. **Settings → Actions → General:** allow GitHub Actions. *Workflow permissions* can stay at **Read repository
   contents**; the workflow asks for write access only to save the item and roster caches.
4. In the **private ledger repository**, set the variable `CDKP_PUBLIC_REPO` to this repository, `CDKP_PUBLIC_PATH`
   to `data`, and the secret `CDKP_PUBLIC_REPO_TOKEN` to a fine-grained token with **Contents: Read and write** on
   this repository only. Its publish workflow then pushes `data/` here after every approved ledger merge.
5. Add the secrets and variables below under **Settings → Secrets and variables → Actions**. All are optional.

| Name | Kind | Needed for | Value |
|---|---|---|---|
| `RAIDHELPER_API_KEY` | Secret | Raid calendar | Server API key from Raid-Helper's `/apikey` command |
| `CDKP_SITE_URL` | Variable | Search and link previews | The page's address ending in `/`, such as `https://owner.github.io/repo/`. With it the page asks to be indexed and also publishes `sitemap.xml` and `llms.txt`; without it the page stays `noindex` |
| `CDKP_GOOGLE_SITE_VERIFICATION` | Variable | Google Search Console (optional) | The `content` value of Search Console's *HTML tag* verification for the `CDKP_SITE_URL` prefix |
| `CDKP_PAGE_TITLE` | Variable | Page (optional) | Page title; default *Peons with Benefits* |
| `CDKP_SOURCE_URL` | Variable | Page (optional) | `https://` link shown in the page footer |

For Search Console's **HTML file** method instead, commit the downloaded `google*.html` file unchanged at the
repository root. Each deployment copies it to the site's root alongside `index.html`. Verify the URL under
your site prefix (for example `https://owner.github.io/repo/googleTOKEN.html`), then select **Verify** in
Search Console. Keep the file committed after verification so later deployments preserve ownership.

## Changing the page

Edit these files in a commit to `main`; the page rebuilds within a few minutes.

- **Open positions** (`community.json` → `recruitment`): `openings` (class and specs), `expectations`, `apply`
  and the date it was `updated`. A spec is plain text or `{"name": "Holy", "priority": "low"}`, with priority
  `high`, `mid` or `low`, shown as High need / Medium need / Low need. These describe recruitment urgency,
  not DKP loot priority. The supplied openings are all Low need, matching the Guilds of WoW listing confirmed
  on 2026-11-15; update them here when recruitment changes. `apply` lists 1 to 3 `https://` links where people apply;
  the first is the main button. The older single `source` link still works in place of `apply`.
- **Raid-Helper** (`community.json` → `raidHelper`): `serverId` is the Discord server ID, written as text; `days`
  is how far ahead to look (1 to 60). Remove the block to hide the raid calendar.
- **Guild at a glance** (`community.json` → `guild`): `language`, `voice`, `raidSize`, `attendance` and
  `atmosphere` are short public descriptions; `source` is the public listing URL and `updated` its confirmation
  date. The supplied facts were checked against Guilds Forever on 2026-11-16. No attendance target was published;
  do not turn a measured percentage into a guild requirement. Raid focus is separate from the sizes supported
  by the loot rules.
- **Logs reports** (`community.json` → `reports`): an array of `{"run": "ledger-run-id",
  "url": "https://forever.warcraftlogs.com/reports/REPORT_CODE"}`. Use the actual 16-character public report code
  and matching ledger run ID, not this placeholder. A report appears under its raid after a confirmed boss
  record for that run is published. Private journal evidence is never mined for report URLs.
- **Character logs** (`community.json` → `profiles`): map an exact Armory URL slug to
  `{"warcraftLogs": "https://forever.warcraftlogs.com/character/id/ACTUAL_ID"}` (or the character URL copied
  from that site). Use only public profiles. Without an explicit URL, the roster offers **Guild logs**, not
  an invented character link. Raider.IO links use the observed Forever EU PvP route and the full character name;
  not every character has been indexed by that service.
- **Gallery** (`gallery/`): add an image (`.jpg`, `.png` or `.webp`, lower-case name, at most 3 MB) and list it in
  `gallery.json`: `{"image": "first-kill.jpg", "caption": "...", "category": "memory", "date": "2026-11-15",
  "alt": "..."}`. `category` is `memory` or `event`; raid kills come from the ledger by themselves. Post only
  pictures that the people in them are happy to have public.

## What this does not do

- It is public. Everything in this repository and on the page can be read by anyone. Keep notes, findings and
  Discord or Battle.net identities in the private ledger repository.
- Nothing here checks the ledger. The page shows what the private repository mirrored after its own checks.
- The page loads Wowhead's tooltip script and icons for looted items; Wowhead sees the visitor's address as with
  any embed. It embeds no other sites: Discord is only linked.
- GitHub turns off scheduled workflows in a public repository after 60 days without activity. If the page stops
  refreshing, enable **CappedDKP site** again under **Actions**.

## Ledger reference

The public page keeps this guidance here instead of displaying an "About this page" disclaimer.

- The approved ledger publishes character and account names, DKP balances, recorded class/spec, raid roles and
  awarded loot. BattleTags, Discord identities, free-text notes, disciplinary findings and record authors,
  checkers and approvers stay private. Private records are counted as omitted in `history.json`, not published.
- Recent activity shows DKP, loot, raid-week and roster records. `history.json` includes all non-private records,
  including setup and loot calls, so displayed event numbers can skip.
- **Cap** is the player's current DKP cap. A dash and **Unverified** mean their guild rank has not been confirmed;
  **Not set** means membership is not tracked.
- Use a player's `#` or an event number to share a direct link to that row. Only the newest records appear on
  the page; older ones are in `history.json`.
- Once a ledger is published, the footer links to `standings.json` and `history.json` and shows its fingerprint.
  Officers compare that fingerprint with their own ledger copy; it cannot be recomputed from the public page.
- The raid calendar publishes counts by role; sign-up names and Discord IDs are not published. A current sign-up's
  role/spec may be attached to a unique matching visible roster character, but the dated Armory roster remains
  separate from the ledger and does not imply DKP balances or eligibility. Before the first approved publication,
  standings remain explicitly empty.
- Roster statistics count visible characters, not accounts or raid sign-ups: each class and Tanks / Healers /
  Melee DPS / Ranged DPS / Unknown. Select a raid-role count to see its class breakdown; class counts are not
  broken down by level. Levels remain on individual character entries. Side Hustle characters are excluded from
  every total. Specs prefer the published ledger, then the current Raid-Helper sign-up for a unique matching roster
  character, then the character's Armory talent tree. A declared raid role fills in when its spec is not decisive.
  Mages and Warlocks are always Ranged, Rogues are always Melee, and Survival Hunters are Melee. Other missing,
  conflicting or ambiguous roles stay Unknown, including Feral Druids without Bear/Cat. Expand **View spec counts**
  for saved spec labels.
- **Raid progression** uses all published boss records, not just recent activity or the gallery. It counts
  each boss ordinal once per raid across resets/groups, with the most recent recorded kill time. It is not a
  live Warcraft Logs feed; no record means unknown, not undefeated.
- **Recorded raid attendance** is `attended / eligible` in an optional `attendance` object on each public
  standings player. The private publisher computes it from confirmed boss presence and recorded membership
  intervals. Each raid in an official reset is one opportunity regardless of groups or nights; presence at any
  kill counts once across linked alts, even when DKP is capped. Only opportunities with a kill while registered
  and not departed count. No bench, wipe-night or full-night claims are made. Unknown membership/reset data and
  accounts with no recorded opportunities have no percentage. Older publications without this field still load;
  update the **private ledger toolkit too**, then publish through its normal approved workflow to populate it.
  Presence lists, actors, evidence and disciplinary details remain private.
- **Loot rules** are a member-facing summary of the formal Capped DKP Loot Rules checked 2026-11-16, with the
  280/100 caps, five Need groups, fixed prices, negative balances, Greed fallback and exceptional paths.
  Update `loot_rules_section` in the source toolkit when policy changes; the formal rules and published tier
  matrix remain authoritative. This page neither declares addon cutover nor enforces awards in game.

## When something fails

Open the failed run under **Actions**; the log says which step failed and why. A problem with one community source
does not fail the run. To refresh the tools, run `tools/capped_dkp_scaffold.py --public --out <this checkout>
--update` from a newer CappedDKP copy, review the diff and commit it.
